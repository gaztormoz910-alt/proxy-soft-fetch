1. `ProxyUtils.fetch_url()` → `parse_proxies()` — весь сбор прокси. Ошибка здесь = нулевой результат всего прогона.

3. `ProxyHunter.advanced_filter()` — гео/ASN-классификация, ping/speed/SMTP-фильтры.
4. `ProxyHunterApp._run_checker_thread()` / `check_one()` — ручной чекер, до 1000 ОС-потоков.
5. `_flush_log()` / `_parse_stats()` — единственный канал данных из backend в UI.

### 🟠 HIGH

#### COR-01 | `fetch_proxy.py:950-956` | Корректность | **high**

**Суть.** `fetch_url()` для любого ответа с `Content-Type: application/json` (или URL на `.json`)
возвращает `str(resp.json())` — то есть **Python-repr словаря** с одинарными кавычками. После этого
`parse_proxies()` не может разобрать такой текст **вообще**: JSON-ветка падает (это не JSON), а
regex-фолбэк `PROXY_RE` требует, чтобы порт шёл сразу за IP через `[:\s,;|"']`, а в repr между ними
стоит `', 'port': `.

**Как воспроизвести (проверено на живом API):**
```
url = https://proxylist.geonode.com/api/proxy-list?limit=20&page=1&...
Content-Type: application/json; charset=utf-8
parse_proxies(сырой текст ответа)  -> 20 прокси
parse_proxies(fetch_url(url))      ->  0 прокси
```

**Масштаб.** Под удар попадают ≈ **220 из 1710 источников** (13 %): 188 страниц Geonode
(до 500 прокси на страницу = до 94 000 прокси за прогон), 13 URL на `.json`, 11 с `format=json/csv`,
8 checkerproxy.net. Это самая дорогая потеря данных в проекте.

**Предлагаемое исправление.** Не «сплющивать» JSON: вернуть `resp.text` как есть (JSON-ветка
`parse_proxies` разберёт его правильно). Ветка с `resp.json()` вообще не нужна.

**Риск фикса.** Низкий, но меняет наблюдаемый результат: прокси станет заметно больше. См.
«Требует решения», вопрос 4.

#### COR-02 | `fetch_proxy.py:1343-1351`, `1611-1626` | Корректность | **high**

**Суть.** Если `GeoLite2-Country.mmdb` не открылась (не скачалась, битая, нет `maxminddb`),
`_get_country()` возвращает `'Unknown'`. В `validate()` дальше идёт жёсткий фильтр
`if country.upper() not in self.countries: return None`, а `self.countries` **никогда не пуст**
(есть список по умолчанию из 30 стран). Значит **каждый** кандидат отбрасывается — прогон молча
даёт 0 прокси, при этом в логе нет ни одной ошибки, только «Живых прокси: 0».

**Как воспроизвести.**
```python
h = ProxyHunter(threads=1); h.db_reader = None
h._get_country('8.8.8.8')      # -> 'Unknown'
'UNKNOWN' in h.countries       # -> False  => validate() выкидывает всё
```

**Предлагаемое исправление.** Если `db_reader is None` — не применять гео-фильтр на этапе
`validate()` (страна всё равно уточняется позже через ip-api.com в `advanced_filter`), и напечатать
явное предупреждение. Плюс: в `run()` при неудачном скачивании базы выводить видимую ошибку, а не
только строку `db_error`.

**Риск фикса.** Средний: меняется поведение при отсутствии базы (было «0 результатов», станет
«результаты без гео-фильтра на первом проходе»). Требует вашего согласия — вопрос 5.

#### COR-03 | `fetch_proxy.py:1986-1988` | Корректность | **high**

**Суть.** `self._speed_sem = asyncio.Semaphore(30)` создаётся лениво и **переиспользуется во втором
проходе**, который крутится в **другом** event loop (`validate()`/`advanced_filter()` каждый раз
создают новый цикл, [fetch_proxy.py:2277-2287](fetch_proxy.py:2277)). `asyncio.Semaphore` привязывается
к первому циклу, где реально ждал, и во втором бросает
`RuntimeError: … is bound to a different event loop`. Исключение глотается `except Exception: pass`,
`speed_ok` остаётся `False` → **все сгенерированные прокси проваливают фильтр скорости**.

**Как воспроизвести.**
```python
# два прогона main_loop в разных циклах с одним и тем же семафором
pass 1: OK
pass 2: RuntimeError: <asyncio.locks.Semaphore …[locked]> is bound to a different event loop
```
Условие срабатывания: `min_speed > 0` (дефолт 1.0 Мбит/с) + включена генерация рандомных прокси.

**Предлагаемое исправление.** Создавать семафор внутри `main_loop()` и передавать его в
`async_run_single_filter`, либо сбрасывать `self._speed_sem = None` в начале каждого `main_loop`.

**Риск фикса.** Низкий. Нужен regression-тест на два последовательных цикла.

#### COR-04 | `gui.py:4033-4041` + `fetch_proxy.py:2110,2300` | Корректность | **high**

**Суть.** Backend печатает `    [REALTIME_REMOVE_LIVE]|{proto}|{ip}|{port}` — с **лидирующим `|`**.
GUI делает `split("[REALTIME_REMOVE_LIVE]")[1].strip().split("|")` и получает
`['', 'http', '1.2.3.4', '8080']`, но читает поля как `parts[0]/parts[1]/parts[2]` — сдвиг на 1.

**Как воспроизвести.**
```
строка : '    [REALTIME_REMOVE_LIVE]|http|1.2.3.4|8080'
parts  : ['', 'http', '1.2.3.4', '8080']
GUI    : {'ip': 'http', 'port': '1.2.3.4', 'protocol': ''}
надо   : {'ip': '1.2.3.4', 'port': '8080', 'protocol': 'http'}
```
Следствие: ключ в `to_remove` ([gui.py:3879](gui.py:3879)) никогда не совпадает с реальными записями,
и прокси, отбракованные строгим фильтром стран в `advanced_filter`, **остаются в таблице и в счётчике
«Рабочие»**. GUI показывает больше прокси, чем реально сохранено в `alive.txt`.

**Предлагаемое исправление.** Читать `parts[1]/parts[2]/parts[3]` (или убрать лидирующий `|` в
backend — но это меняет формат IPC, лучше править GUI).

**Риск фикса.** Низкий. Нужен характеризующий тест на парсер маркеров.

#### COR-05 | `fetch_proxy.py:1391-1425`, `1446-1454`, `1490-1524` | Корректность / Надёжность | **high**

**Суть.** Сбор источников идёт в `with ThreadPoolExecutor(max_workers=50) as ex:`. При отмене код
делает `break` из цикла `as_completed`, но выход из `with` вызывает `shutdown(wait=True)` **без
`cancel_futures`**. В очереди к этому моменту висят до 1710 задач, каждая с таймаутом ≥ 15 с →
отмена «залипает» на минуты, GUI при этом уже показал «Задача отменена».

**Почему это баг.** Кнопка «Отмена» не отменяет. То же в блоке «Машины времени» GitHub.

**Предлагаемое исправление.** Явный `ex.shutdown(wait=False, cancel_futures=True)` в `finally`
(или ручной `fut.cancel()` для незапущенных) + проверка `_cancel_event` в начале `_fetch_and_parse`.

**Риск фикса.** Низкий.

#### SEC-02 | `fetch_proxy.py:946` | Безопасность | **high**

**Суть.** `requests.get(..., verify=False)` + глобальный `urllib3.disable_warnings()` — TLS-проверка
отключена для **всех 1710 источников**, включая `raw.githubusercontent.com` и `cdn.jsdelivr.net`.

**Почему это баг.** Активный MITM (публичный Wi-Fi, скомпрометированный провайдер, корпоративный
перехват) может подменить содержимое любого источника и подсунуть свои «прокси» — то есть
подконтрольные ему точки выхода, через которые пользователь потом погонит трафик. Классическая
цепочка компрометации; при этом никакой ошибки пользователь не увидит.

**Предлагаемое исправление.** `verify=True` по умолчанию; при `SSLError` — один retry с
`verify=False` **только** если пользователь явно включил флаг «разрешить небезопасные источники»,
с записью в лог.

**Риск фикса.** Средний: часть источников с самоподписанными/просроченными сертификатами
перестанет отвечать. Нужно ваше решение — вопрос 2.

#### COR-06 | `fetch_proxy.py:723-724`, `744-843` | Корректность | **medium**

**Суть.** Классовые регулярки `JSON_IP_FIRST` и `JSON_PORT_FIRST` определены, но **нигде не
используются** — это мёртвый код. Именно из-за их отсутствия regex-фолбэк не умеет вытаскивать
прокси из JSON-подобного текста: `PROXY_RE` не «перепрыгивает» через `","port":"`.

**Как воспроизвести.**
```python
# оборванный (стрим обрезан по таймауту / лимиту 20 МБ) но валидный по данным JSON
c = '{"data":[{"ip":"1.2.3.4","port":"8080"},{"ip":"5.6.7.8","por'
parse_proxies(c)  # -> []   (ожидается ['1.2.3.4:8080'])

# одна битая запись убивает весь источник
bad = '{"data":[{"ip":"².1.1.1","port":"80"},{"ip":"8.8.8.8","port":"3128"}]}'
parse_proxies(bad)  # -> []   (ожидается ['8.8.8.8:3128'])
```

**Предлагаемое исправление.** (а) добавить `JSON_IP_FIRST`/`JSON_PORT_FIRST` в regex-фолбэк;
(б) в `extract_from_json` обернуть разбор одного узла в try/except, чтобы битая запись не роняла
весь источник.

**Риск фикса.** Низкий; увеличит количество найденных прокси (см. вопрос 4).

#### COR-07 | `fetch_proxy.py:727-742` | Корректность | **medium**

**Суть.** `is_valid()` использует `p.isdigit()`, который истинен для **любых** Unicode-цифр.

**Как воспроизвести.**
```python
is_valid('٣.1.1.1', 80)   # -> True   (арабо-индийская цифра принята как IP)
is_valid('².1.1.1', 80)   # -> ValueError: invalid literal for int() … '²'
```
Первый случай пропускает мусор в список прокси, второй бросает необработанное `ValueError` внутри
`extract_from_json` и обрывает разбор всего источника (см. COR-06).

**Предлагаемое исправление.** Заменить `p.isdigit()` на строгую проверку ASCII
(`p.isascii() and p.isdecimal()`), заодно запретить ведущие нули (`'01.2.3.4'`).

**Риск фикса.** Низкий.

#### COR-11 | `gui.py:1499-1507` | Корректность | **medium**

**Суть.** При переключении языка `_translate_vals()` определяет ISO-код страны **подстрочным
поиском**: `if name in current_c`. Названия стран часто вложены друг в друга.

**Почему это баг.** `"Niger" in "Nigeria"` → True. В зависимости от порядка обхода словаря
Нигерия (NG) превратится в Нигер (NE). Аналогично: `Guinea` ⊂ `Papua New Guinea` /
